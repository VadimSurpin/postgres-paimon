# Разбор SQL-расширения paimon_slot

Исходный файл: [paimon_slot--1.0.sql](../sql/paimon_slot/paimon_slot--1.0.sql).
Руководство по всей системе: [logical-slot-architecture.md](logical-slot-architecture.md).

Этот документ объясняет PostgreSQL-часть репликации в Apache Paimon: служебные таблицы,
регистрацию источников, передачу изменений схемы, защитные ограничения и диагностику.
Номера строк в ссылках соответствуют версии исходника на момент написания и могут смещаться.

## 1. Назначение файла и установка

SQL-файл устанавливает объекты, которые остаются в базе и используются при дальнейшей работе.
Он сам не копирует строки в Paimon и не запускает Java writer.

Правильный способ установки:

```sql
CREATE EXTENSION paimon_slot;
```

В начале файла стоит защита от прямого запуска через psql:

```sql
\echo Use "CREATE EXTENSION paimon_slot" to load this file. \quit
```

PostgreSQL читает [paimon_slot.control](../sql/paimon_slot/paimon_slot.control), где заданы
схема `paimon` и требование установки суперпользователем, затем выполняет установочный SQL.

Распределение обязанностей:

| Компонент | Обязанность |
|---|---|
| Ядро PostgreSQL | Записывает обычные изменения строк в WAL |
| Расширение paimon_slot | Регистрирует таблицы, проверяет совместимость, отправляет события схемы |
| Публикация paimon_pub | Определяет, изменения каких таблиц передавать |
| Логический слот | Хранит позицию потребителя и удерживает необходимый WAL |
| Java writer | Читает поток, пишет данные и историю в Paimon, подтверждает обработанную позицию |

Сам рабочий слот создаёт writer, а не этот установочный SQL-файл.

## 2. Служебные таблицы

### table_registry — действующие регистрации

Определение: [строка 17](../sql/paimon_slot/paimon_slot--1.0.sql#L17).

Одна строка соответствует таблице PostgreSQL, подключённой к репликации.

| Поле | Значение |
|---|---|
| `relid` | OID исходной таблицы PostgreSQL, первичный ключ реестра |
| `schema_name`, `table_name` | Имена назначения, зафиксированные при регистрации |
| `pk_cols` | Колонки первичного ключа в порядке ключа |
| `cols` | JSON с колонками, идентификаторами полей и типами |
| `backfill_due` | Нужна ли загрузка существующих строк |
| `replica_identity` | Режим идентификации старой строки; поддерживается `full` |
| `changelog_producer` | Режим changelog; поддерживается `input` |
| `buckets` | Число бакетов основной таблицы |
| `registered_at` | Время регистрации |
| `hist_table` | Имя таблицы истории, обычно `<table>_hist` |
| `registration` | UUID конкретной регистрации |
| `hist_buckets` | Выбранное число бакетов истории в каждой дневной партиции |
| `hist_buckets_user` | Явно заданное пользователем число бакетов истории, если оно задано |

Реестр нужен для запуска writer, сравнения схемы до и после DDL, управления первоначальной
загрузкой и защиты от конфликтов имён. Публикация этих сведений не хранит.

`cols` описывает зарегистрированную структуру источника. Это не подтверждение, что writer уже
применил эту схему в Paimon: потребитель может отставать.

### retained_history — история отключённых или удалённых таблиц

Определение: [строка 55](../sql/paimon_slot/paimon_slot--1.0.sql#L55).

После `DROP TABLE` или `paimon.remove_table()` история в Paimon сохраняется. Реестр
`retained_history` резервирует её имя и имена архивов, чтобы новая таблица не продолжила
чужую историю изменений.

Например, удаление `orders` не освобождает автоматически имя `orders_hist` для новой
регистрации другой таблицы с именем `orders`.

### kept_tables — сохранённые основные таблицы

Определение: [строка 77](../sql/paimon_slot/paimon_slot--1.0.sql#L77).

`remove_table()` сохраняет основную таблицу Paimon. Если источник подключают снова,
расширение проверяет, что его ключ совместим с сохранённой таблицей.

Таблица с первичным ключом и журнал операций без ключа имеют разную структуру хранения.
Продолжать запись после незаметной смены ключа было бы некорректно.

### secret — токен служебных сообщений

Определение: [строка 237](../sql/paimon_slot/paimon_slot--1.0.sql#L237).

Таблица содержит токен, добавляемый к сообщениям расширения. Уникальный индекс по константе
не позволяет хранить более одной строки. Публичный доступ к таблице отозван.

Вызовы `pg_extension_config_dump()` для реестров отмечают их содержимое как конфигурацию
расширения для pg_dump.

## 3. Чтение структуры и преобразование типов

### pg_type_to_paimon()

Определение: [строка 90](../sql/paimon_slot/paimon_slot--1.0.sql#L90).

Функция преобразует тип PostgreSQL в строковое описание типа Paimon.

| PostgreSQL | Paimon |
|---|---|
| `boolean` | `BOOLEAN` |
| `smallint`, `integer`, `bigint` | `SMALLINT`, `INT`, `BIGINT` |
| `real`, `double precision` | `FLOAT`, `DOUBLE` |
| `numeric(p,s)` | `DECIMAL(p,s)` |
| `text`, `varchar`, `char`, `uuid` | `STRING` |
| `bytea` | `BYTES` |
| `date` | `DATE` |
| `timestamp` | `TIMESTAMP` |
| `timestamptz` | `TIMESTAMP WITH LOCAL TIME ZONE` |

Остальные типы получают `STRING` с предупреждением. Возможность получить строковое описание
не означает, что тип разрешён: дополнительные проверки могут запретить его регистрацию.

### table_cols(), wire_cols(), pk_cols()

`table_cols()` читает живые пользовательские колонки из `pg_attribute` и собирает JSON:

```json
[
  {
    "id": 1,
    "name": "id",
    "type": "INT NOT NULL",
    "typid": 23,
    "typmod": -1
  }
]
```

`id` берётся из `attnum`: переименование колонки не меняет её идентификатор.
Удалённые колонки исключаются, а оставшиеся номера не перенумеровываются.

`typid` и `typmod` сохраняют исходный PostgreSQL-тип и его параметры. Они нужны для проверки
DDL: например, `varchar` и `char` отображаются в `STRING`, но преобразования между ними могут
изменять значения.

`wire_cols()` удаляет внутренние поля `typid` и `typmod` перед передачей writer.
`pk_cols()` возвращает массив имён колонок ключа в порядке ключа либо пустой массив.

## 4. Публикация и запись событий в WAL

Определение публикации: [строка 212](../sql/paimon_slot/paimon_slot--1.0.sql#L212).

```sql
CREATE PUBLICATION paimon_pub
    WITH (
        publish = 'insert, update, delete, truncate',
        publish_via_partition_root = false
    );
```

Изначально отслеживаемых таблиц в ней нет. Их добавляет `add_table()`.

Есть два разных пути передачи событий:

```text
INSERT / UPDATE / DELETE / TRUNCATE
    → PostgreSQL автоматически пишет WAL
    → pgoutput декодирует изменения опубликованных таблиц
    → writer получает события данных

Изменение схемы
    → event trigger расширения
    → JSON с описанием изменения
    → paimon.emit()
    → pg_logical_emit_message()
    → writer получает событие схемы
```

Публикация определяет, что передавать потребителю. Обычное журналирование таблиц выполняет
ядро PostgreSQL независимо от регистрации в paimon_slot.

### emit()

Определение: [строка 253](../sql/paimon_slot/paimon_slot--1.0.sql#L253).

Функция вызывает:

```sql
SELECT pg_logical_emit_message(
    true,
    'paimon',
    (payload || jsonb_build_object(
        'auth', (SELECT token FROM paimon.secret)
    ))::text
);
```

- `true` означает транзакционное сообщение: откатившаяся транзакция не должна применяться
  writer как зафиксированное событие.
- `paimon` — префикс сообщений.
- JSON содержит операцию, параметры и токен проверки.

Один префикс не доказывает происхождение сообщения: поэтому writer проверяет токен.
У `emit()` отозван публичный доступ. Токен не защищает от ролей, способных прочитать секрет.

## 5. Проверки совместимости и ограничения значений

Цель защитного кода — не допустить ситуацию, когда PostgreSQL уже зафиксировал изменение,
но writer не может применить его в Paimon и останавливается на одной записи.
В комментариях такая запись называется poison record.

### Проверки структуры

`reject_unsafe_numeric()` запрещает неподдерживаемые варианты numeric:

- без заданной точности;
- с точностью больше 38;
- с отрицательным scale;
- со scale больше precision.

`reject_unsupported_column()` запрещает generated columns и типы семейства `regclass`,
`regtype` и другие `reg*`, включая проверяемые вложенные формы.

Причина запрета `regclass`: его текст зависит от имени другого объекта. Переименование
этого объекта изменяет отображение значений без UPDATE исходных строк, поэтому writer
не получает события для обновления Paimon.

`reject_unsafe_identity()` проверяет имена таблиц и схем. Например, `/` может превратить
имя таблицы во вложенный путь, `$` имеет специальный смысл в имени таблицы Paimon,
а `sys` зарезервирован как системная база Paimon.

### CHECK constraints: paimon_guard_<attnum>

Основная функция: [add_guards(), строка 490](../sql/paimon_slot/paimon_slot--1.0.sql#L490).

Для отдельных типов создаются ограничения на значения. Например:

```sql
CONSTRAINT paimon_guard_2 CHECK (amount <> 'NaN'::numeric)
```

Для timestamp и timestamptz ограничивается верхняя граница конечных значений, которые
writer способен записать. Значение `infinity` обрабатывается отдельно и разрешено.

При регистрации ограничения проверяют существующие строки. Для новых или безопасно
преобразованных колонок они могут добавляться как `NOT VALID`: новые записи проверяются,
а старые строки повторно не сканируются.

`guard_present()` проверяет имя, выражение и признак `ENFORCED`. Совпадение имени при
`CHECK (true)` либо `NOT ENFORCED` не считается действующей защитой.

## 6. Регистрация таблицы: add_table()

Определение: [строка 713](../sql/paimon_slot/paimon_slot--1.0.sql#L713).

Пример:

```sql
SELECT paimon.add_table(
    'public.orders'::regclass,
    buckets => 8,
    hist_buckets => 2
);
```

Последовательность действий:

1. Проверить параметры. В этой версии доступны только `replica_identity = 'full'`
   и `changelog_producer = 'input'`.
2. Проверить, что объект — обычная таблица и ещё не зарегистрирован.
3. Взять блокировку `SHARE ROW EXCLUSIVE` до чтения ключа и колонок.
4. Прочитать ключ и структуру.
5. Проверить типы, имена, конфликты истории, сохранённую основную таблицу и наследование.
6. Запретить `DEFERRABLE` primary key.
7. Проверить наличие строк и определить `backfill_due`.
8. Выбрать число бакетов.
9. Включить `REPLICA IDENTITY FULL`.
10. Добавить и проверить ограничения значений.
11. Выполнить `ALTER PUBLICATION paimon_pub ADD TABLE ONLY ...`.
12. Записать регистрацию в `table_registry`.
13. Отправить сообщение `create` с колонками, ключом, настройками и UUID регистрации.

Блокировка конфликтует с записью и защищает проверку наличия строк от гонки.
Последующие ALTER внутри функции также могут требовать более сильных блокировок.

Порядок действий важен: служебные ALTER выполняются до добавления строки в реестр.
Иначе event trigger воспримет собственную настройку расширения как изменение уже
отслеживаемой таблицы.

Таблицы без первичного ключа разрешены: writer создаёт для них журнал операций вместо
основной таблицы с актуальным состоянием.

`add_table()` не делает первоначальное копирование сама. Если при существующем слоте
зарегистрировать непустую таблицу, функция может завершиться успешно, но writer на
следующем старте потребует повторный bootstrap для согласованной загрузки.

## 7. Выбор числа бакетов

`default_buckets()` для основной таблицы использует формулу:

```text
clamp(4, ceil(размер таблицы / 1 GiB), 64)
```

Для истории `hist_buckets_for()` использует:

```text
clamp(1, ceil(объём истории за день / 1 GiB), 64)
```

Дневной объём оценивается по статистике:

```text
(INSERT + 2 × UPDATE + DELETE) / число дней × средний размер строки
```

UPDATE учитывается дважды из-за старого и нового образов строки.
Если статистики недостаточно, оценка строится по размеру таблицы.
Число бакетов истории задаётся на каждую дневную партицию, поэтому слишком большое
значение увеличивает число файлов во всех днях.

Явные `buckets` и `hist_buckets` позволяют переопределить оценку.
SQL выбирает настройки; физические таблицы и файлы создаёт writer через Paimon.

## 8. Изменение схемы: sync_table()

Определение: [строка 1192](../sql/paimon_slot/paimon_slot--1.0.sql#L1192).

После DDL функция сравнивает:

```text
Старая структура → table_registry.cols
Новая структура → системные каталоги PostgreSQL
```

Сопоставление выполняется по идентификатору поля `attnum`. Поэтому переименование
отличается от удаления колонки и добавления другой.

Сначала проверяются ограничения:

- первичный ключ не изменился и не стал DEFERRABLE;
- replica identity осталась FULL;
- защитные constraints сохранены;
- новые колонки имеют допустимые имена и типы;
- новая колонка не имеет DEFAULT или запрещённого NOT NULL;
- тип ключевой колонки не меняется на другой тип Paimon;
- nullable-колонка не становится NOT NULL;
- преобразование типа не меняет уже сохранённые значения несовместимым образом.

Допускаются определённые точные расширения типов, например smallint → integer → bigint,
real → double precision, расширение допустимой точности numeric или длины varchar.

Сообщения отправляются в порядке:

```text
drop_col → rename_col / alter_col → add_col
```

Так удалённое имя освобождается до повторного использования.
Затем обновляется `table_registry.cols` и добавляются необходимые ограничения значений.
Реестр обновляется до внутреннего ALTER с constraints, чтобы повторный вход в триггер
не отправил те же сообщения снова.

Проверка работает после DDL, когда новая структура уже видна в каталогах, но ещё внутри
той же транзакции. Исключение откатывает DDL, изменения реестра и транзакционные сообщения.

## 9. Event triggers

| Триггер | Событие | Задача |
|---|---|---|
| `paimon_ddl_end` | `ddl_command_end` | Проверять и передавать изменения схемы |
| `paimon_table_rewrite` | `table_rewrite` | Блокировать неподдерживаемые преобразования строк |
| `paimon_sql_drop` | `sql_drop` | Обрабатывать удаления таблиц и колонок |

### on_ddl_end()

Определение: [строка 1412](../sql/paimon_slot/paimon_slot--1.0.sql#L1412).

Вызывает `sync_table()` для затронутых таблиц, их потомков и при необходимости родителей.
Это важно, когда ALTER родителя меняет зарегистрированную дочернюю таблицу или партицию.

Также проверяет изменения constraints, публикаций и типов.
Например, переименование используемого enum label запрещается: текст существующих
значений изменился бы без UPDATE, а Paimon сохранил бы старую метку.
Проверка использования типа проходит и через массивы, домены и другие вложенные типы.

### on_table_rewrite()

Определение: [строка 1521](../sql/paimon_slot/paimon_slot--1.0.sql#L1521).

Операция вида:

```sql
ALTER TABLE orders
ALTER COLUMN amount TYPE bigint USING amount * 100;
```

может переписать значения физически, не создавая для логического потребителя обычный
поток UPDATE. Paimon остался бы со старыми значениями.

Обработчик проверяет причину rewrite и текст запроса, блокирует USING и некоторые
вложенные операции, где нельзя надёжно определить преобразование. Проверка текста
консервативна и имеет описанные в исходнике остаточные ограничения; это не полноценный
SQL-парсер.

### on_sql_drop()

Определение: [строка 1566](../sql/paimon_slot/paimon_slot--1.0.sql#L1566).

При удалении зарегистрированной таблицы:

1. Отправляет `drop_table` с зафиксированным именем назначения.
2. Запоминает сохраняемую историю.
3. Удаляет регистрацию.

Если каскадное удаление затронуло колонку сохранившейся таблицы, вызывает `sync_table()`.
Также контролирует, чтобы удаление объектов публикации не отключило репликацию незаметно.

Все три триггера включены как `ENABLE ALWAYS`, в том числе для режима
`session_replication_role = replica`. Суперпользователь всё равно может отключить их явно;
это должна обнаружить диагностика.

## 10. Защита публикации

`publication_problems()` и `check_publication()` проверяют, что:

- публикация существует;
- включены INSERT, UPDATE, DELETE и TRUNCATE;
- `publish_via_partition_root` не включён;
- каждая зарегистрированная таблица присутствует;
- у неё нет фильтра строк;
- список публикуемых колонок не исключает живые колонки.

Изменение публикации, нарушающее эти условия, откатывается с ошибкой.
Иначе пользователь мог бы отключить часть потока, а writer продолжал бы работать
без очевидных признаков потери изменений.

## 11. Имена и сохранённая история

`reject_reserved_name()` запрещает колонки, конфликтующие со служебными полями Paimon
или writer, включая `_seq`, `_op`, `_commit_lsn`, `_lsn`, `_op_seq`, `_xid`, `_ts`, `_dt`.
Ряд проверок выполняется без учёта регистра, поскольку Spark и Flink обычно разрешают
имена колонок без учёта регистра.

`hist_name()` строит имя `<table>_hist`.
`is_history_of()` распознаёт текущую историю и архивы вида:

```text
orders_hist
orders_hist_00000000016E3A40
```

`reject_name_collision()` проверяет пересечения основных таблиц, историй и сохранённых
историй. `registration` позволяет writer дополнительно проверить принадлежность
фактической таблицы истории в warehouse конкретной регистрации.

Сама SQL-часть не видит файлов Paimon и не может проверить все конфликты в хранилище.

Имя назначения фиксируется при регистрации. Последующие RENAME TABLE или SET SCHEMA
в PostgreSQL не перемещают Paimon-таблицу: исходная таблица отслеживается по OID.

## 12. Отключение и удаление таблиц

`remove_table()` определена на [строке 844](../sql/paimon_slot/paimon_slot--1.0.sql#L844).

Она запоминает историю и основную Paimon-таблицу, удаляет регистрацию, исключает источник
из публикации и снимает принадлежащие расширению ограничения значений.

Реестр удаляется до снятия публикации и constraints: иначе защитные триггеры запретили бы
эти действия для ещё зарегистрированной таблицы.

| Действие | Исходная таблица | Основная таблица Paimon | История Paimon |
|---|---|---|---|
| `paimon.remove_table()` | Сохраняется | Сохраняется | Сохраняется |
| `DROP TABLE` | Удаляется | Writer получает команду удалить | Сохраняется |

`forget_history()` и `forget_kept_table()` удаляют служебные записи после ручной обработки
сохранённых таблиц. Они не удаляют данные Paimon и не проверяют warehouse.
При освобождении имени истории нужно учитывать и её архивы.

## 13. Первоначальная загрузка и повторный bootstrap

`backfill_due` означает необходимость загрузить существующие строки.
После успешной записи первоначальной загрузки writer вызывает `mark_backfilled()`:

```sql
UPDATE paimon.table_registry
SET backfill_due = false
WHERE relid = rel::oid;
```

Этот флаг не хранит позицию WAL.

При повторном bootstrap [rebootstrap.sh](../scripts/rebootstrap.sh) удаляет неактивный
слот и помечает все регистрации `backfill_due = true`. После запуска writer создаёт
новый слот и снимок и загружает таблицы заново.

Существующая история сохраняется, но промежуточные изменения за пропущенный период
не восстанавливаются: загрузка отражает состояние на момент нового снимка.

## 14. Диагностика

### health()

Определение: [строка 1651](../sql/paimon_slot/paimon_slot--1.0.sql#L1651).

```sql
SELECT * FROM paimon.health();
```

Проверяет триггеры, публикацию, существование исходных таблиц, replica identity,
совпадение структуры с реестром, ограничения значений, наследование и конфликты истории.

Одна строка результата — одна найденная проблема. Пустой результат означает, что эти
проверки проблем не обнаружили. Это не построчное сравнение PostgreSQL и Paimon.

### slot_health()

Определение: [строка 1731](../sql/paimon_slot/paimon_slot--1.0.sql#L1731).

```sql
SELECT * FROM paimon.slot_health();
```

Проверяет слот в `pg_replication_slots` и старые prepared transactions.

| Уровень | Значение |
|---|---|
| `fatal` | Слот отсутствует, недействителен или имеет неподходящий тип, плагин либо базу |
| `warning` | Повышенное удержание WAL, риск инвалидирования или старая prepared transaction |
| `down` | К слоту не подключён writer |

В режиме `for_writer` отсутствие слота и подключения трактуется с учётом того, что
writer ещё только собирается создать слот или подключиться.
Функции диагностики сообщают проблемы, но сами их не исправляют.

## 15. Безопасность и тестовый помощник

У функций закреплён путь поиска:

```sql
SET search_path = pg_catalog, pg_temp
```

Это препятствует подмене объектов через пользовательские схемы, особенно при выполнении
кода с повышенными правами.

Три обработчика событий объявлены `SECURITY DEFINER`: они используют права владельца,
чтобы обычный владелец таблицы мог выполнять допустимый DDL без доступа к секрету
и внутренним функциям расширения. У чувствительных помощников отозван публичный доступ.

`peek_messages()` — тестовая функция. Она читает и потребляет сообщения отдельного слота
`paimon_test`, исключая случайные токен и UUID из результата тестов. Рабочий writer её
не использует. Несмотря на имя peek, это потребление через `pg_logical_slot_get_changes()`.

## 16. Сквозной пример

```sql
CREATE TABLE orders (
    id int PRIMARY KEY,
    amount numeric(12,2)
);

SELECT paimon.add_table('orders'::regclass);

INSERT INTO orders VALUES (1, 100);

ALTER TABLE orders ADD COLUMN status text;

UPDATE orders SET status = 'paid' WHERE id = 1;
```

При корректно настроенной системе и работающем writer последовательность такая:

```text
add_table()
  → проверяет структуру и существующие значения
  → включает FULL и ограничения
  → добавляет источник в публикацию и реестр
  → отправляет create

INSERT
  → PostgreSQL автоматически записывает изменение в WAL

ALTER TABLE
  → event trigger сравнивает старую и новую схему
  → отправляет add_col
  → обновляет реестр

UPDATE
  → PostgreSQL пишет изменение с полным старым образом строки

Java writer
  → читает события и данные
  → применяет схему в Paimon, архивируя историю при изменении колонок
  → записывает данные и историю
  → подтверждает обработанную позицию после записи
```
